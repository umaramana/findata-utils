Review Agent — Architecture Sketch
Status: Draft. [FILL] sections need Uma's judgment. Purpose: Decide what the finished agent is, so individual builds stop drifting. Last revised: 22 Sep 2026 — amendment note added after §4.1 (see inline). Prior: 26 Aug 2026 — §4.1 added and §7 re-sequenced after the first manual QA review of a live return.

1. What the agent is
A first-level reviewer that runs a set of independent checks over a prepared return and produces one report. Suresh sees flagged returns; clean ones are pre-cleared for spot-check.

It is not a preparer, and it does not judge whether a tax position is correct. It checks that what was entered matches what was supplied, and that the result is internally plausible.

2. The checks
Derived from what Suresh actually reviews today (established May 2026).

#	Check	Question it answers
1	Document completeness	Did everything the client supplied get entered?
2a	Internal plausibility	Is the result implausible on its face? (zero tax on high income, withholding out of proportion to wages)
2b	Year-over-year variance	Did something swing unexpectedly vs. prior year?
3	Anomaly rules	Are deductions/credits outside normal bounds, or present without their preconditions?
4	Document-to-return matching	Do the numbers on source documents match the return?
3. Shared capabilities
The checks are not five separate tools. They sit on three capabilities:

┌─────────────────────────────────────────────────────┐
│  CHECKS (rules + comparison logic)                  │
│  1 completeness   2a plausibility   2b variance     │
│  3 anomalies      4 doc matching                    │
└─────────────────────────────────────────────────────┘
                        ↑
┌─────────────────────────────────────────────────────┐
│  CAPABILITIES (extraction — shared)                 │
│                                                     │
│  A. Drake return parser                             │
│     Print-to-PDF, text layer, pdfplumber            │
│     Feeds: 1, 2a, 2b, 3, 4                          │
│                                                     │
│  B. Source document extractor                       │
│     Local OCR. Standalone W-2 / 1099-INT / 1099-DIV │
│     Feeds: 1, 4                                     │
│                                                     │
│  C. Brokerage summary extractor                     │
│     Consolidated 1099 summary page, per brokerage   │
│     Shared with stock processor (see §5)            │
│     Feeds: 1, 4                                     │
└─────────────────────────────────────────────────────┘
Key consequence: capability A feeds every check. Once it exists, checks 2a and 3 are rules over data already parsed — near-free additions, not separate projects.

4. Cost ordering
By input requirement, cheapest first:

Check	Inputs needed	Cost
3 — anomalies	Current return only	Low
2a — internal plausibility	Current return only	Low
4 — doc matching	Current return + source docs (OCR, brokerage layouts, eligibility gate)	High — specced, in progress
2b — year-over-year	Current + prior year return, matched across years	Medium — needs prior-year retrieval
1 — completeness	Document inventory	Blocked on process, not code — no structured intake log exists
4.1 Evidence — manual QA review, one TY2025 return (Aug 2026)
Uma ran a full manual QA of a live return, ~6 hours, 18 open items. This answers the [FILL] that stood here: check 4 is not where review time goes. It is simply the most concrete check.

Where the 18 items fell	Count
Schedule E rental income/expense (6 properties)	7
Client input required (missing ID, unconfirmed K-1, missing substantiation, missing sq ft)	7
Within check 4's specced scope (1099-INT, 1099-DIV)	2
Other (Sch F farm income, two 1098s, vehicle mileage, 1099-S)	5
Two further findings:

The return would have failed the §5 eligibility gate anyway — Sch E across six properties, Sch F, home office, 1099-S. A finished v1 would have aborted, not helped. The gate is correct; the scope behind it is too narrow to be useful on the returns that actually take time.
A new discriminator emerged. Discrepancies split into two classes that behave completely differently:
Third-party document exists — the document governs, the return follows it, and the discrepancy is the client's own organizer disagreeing with his documents. Informational. Raise with the client; nothing to fix.
No third-party document — entered from the organizer, with only the client's own workings as a cross-check. This is the only place a real error can hide. 7 of the 18 items, and both of the largest.
This distinction is not in the current design. It should be, and it is nearly free — it is a property of which source a figure came from, which extraction already knows.
Caveat: one return is not a sample. But it is one more than the design had, and it points against the current build order.

5. Relationship to existing tools
Stock processor (findata-utils) — parses consolidated 1099 transaction detail for Drake import. Has a parked feature: validate parsed transactions against statement summary totals.

That parked feature and capability C are the same work. Build once, two consumers:

Stock processor uses summary totals to validate its 1099-B parse
Review agent uses INT/DIV totals from the same summary page for check 4
Build it in the stock processor as a shared extraction layer. Scope it to extraction only — exposing the totals. Validation logic is a separate card.

Transaction Tagger — unrelated. Business bookkeeping, not individual returns.

6. Output
One report per return. [FILL — single consolidated report, or per-check sections? Suresh does not engage with long documents.]

Every check reports what it read, not just what it found. An unread document and an unkeyed document are indistinguishable without the count.

Ineligible returns abort with a reason rather than flagging. A false flag costs more trust than a skipped return.

7. Build sequence
Revised against §4.1. The original order front-loaded check 4 on the assumption it carried the most review time. It does not.

Capability A — Drake return parser. Feeds every check; nothing moves without it. Unchanged as the first real build.
Checks 2a + 3 — plausibility and anomaly rules. Rules over capability A, current return only, no OCR, no source documents, no eligibility gate. Cheapest thing that can ship and the only checks with no external dependency.
Capability B — source document OCR (W-2, standalone 1099-INT/DIV).
Check 4 — doc matching (per SPEC.md), plus the source-class distinction from §4.1.2.
Capability C — brokerage summary extractor, in the stock processor. Still shared work (§5), but it no longer gates the first useful output.
Check 2b — year-over-year, once prior-year retrieval is solved.
Check 1 — completeness, once intake logging exists.
Target: checks 2a + 3 running against last season's completed returns by end September. Check 4 follows. Suresh sees anything post-Oct 15.
